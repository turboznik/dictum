❓ Q19 — Model-download egress boundary: Emptying the generated catalog’s mirrors array prevents fallback to
blob.handy.computer for catalog models. However, the inherited backend still contains roughly 15 hidden legacy model
definitions with direct blob.handy.computer URLs.

Should Dictum prohibit every remote model download except through the model mirror, or is the narrower “never
contact Hugging Face” rule sufficient?

➡️ I recommend prohibiting every non-Dictum model download. Keep already-downloaded legacy models usable, but reject
attempts to download their hard-coded remote URLs. Otherwise the model mirror is not a reliable egress boundary.

❓ Q20 — Model mirror authentication: The current Hugging Face client deliberately sends no credentials. Protecting
model downloads with the post-processing API key would require additional desktop authentication plumbing.

Should the starter model mirror remain unauthenticated?

➡️ I recommend yes. Bind the starter server to loopback only. Corporate adopters can add gateway or network-level
authentication when converting it into a central service.

———

❓ Q21 — Post-processing forwarding policy: Should the gateway transparently pass arbitrary OpenAI-compatible
request fields to OpenRouter, or accept only what Dictum needs?

➡️ I recommend a strict request envelope:

- Accept only messages.
- Force model to openai/gpt-5.6-luna.
- Force stream to false.
- Discard tools, plugins, provider routing, sampling, and other client-controlled options.
- Cap request size and message count.
- Apply a 60-second upstream timeout.
- Never log transcript or response bodies.
- Return generic gateway errors without leaking OpenRouter details.

The public starter credential otherwise creates a paid arbitrary-prompt relay if the server is accidentally exposed.

———

❓ Q22 — Incorrect API-key behavior: With no onboarding validation, the user may enter an incorrect gateway key.
Handy currently falls back to the original transcription and records the failure only in logs, making Post
Processing appear to do nothing.

Should Dictum retain that silent behavior?

➡️ I recommend saving the key without proactive validation, but showing a localized error notification when an actual
post-processing request fails. This avoids a new validation endpoint and Test button while making incorrect
credentials diagnosable.

———

❓ Q23 — Desktop credential storage: Handy stores provider API keys in its ordinary serialized settings file; its
secret wrapper only prevents accidental debug printing. Moving this one credential into Windows Credential Manager
would introduce a new persistence subsystem.

Should Dictum retain Handy’s existing storage behavior for the starter credential?

➡️ I recommend yes. SAFE_FOR_TESTING is explicitly demonstrative authentication, and preserving the inherited
settings mechanism matches the MVP scope. The limitation should be documented for adopters.

———

❓ Q24 — Release-note suppression: Hiding “Show What’s New” and defaulting its setting to false works for fresh
installations. Alternatively, Dictum can also stop mounting the inherited release-note gate, guaranteeing that no
setting or development profile can show Handy release notes.

➡️ I recommend unmounting the gate and leaving the existing release-note machinery dormant. Distribution work can
reconnect it later when Dictum has its own update feed.

———

❓ Q25 — Handy acknowledgement link: Should the new Handy/CJ Pais acknowledgement link to the Handy repository?

➡️ I recommend yes. It preserves useful provenance after the separate upstream “Source Code” row is hidden, without
presenting Handy as Dictum’s source repository. The acknowledgement copy will be genuinely localized across all
supported locales.

———

❓ Q26 — Reset-script recovery: Should the development reset script irreversibly delete Dictum’s data immediately,
or move it into timestamped backups by default?

➡️ I recommend timestamped backups by default, with an explicit --delete option for irreversible cleanup. Both modes
should require Dictum to be closed, print the exact resolved targets, and refuse unsafe paths.
