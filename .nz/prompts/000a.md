## Hugging Face

I believe Handy accesses Hugging Face to fetch the latest open-weight models that it can download. Right? **(I actually want an answer.)**

**I don't want my desktop app accessing Hugging Face!**

This is where the server comes in. Add a folder to the repo called `server`. In it will live a web server that uses Deno. Make that folder a Deno package.

That package shall have a subfolder called `scripts`. In it will be a subfolder called `get-hf`.

That `server/scripts/get-hf/main.ts` script will use the same API endpoint/whatever (I don't know how it works) as the Handy desktop app to:

- Check for available models.
- **Selectively** download the assets and data necessary for it to act as a proxy (to replace Hugging Face) to the folder `server/scripts/get-hf/data`. That `data` folder will be tracked by Git, but its contents (except for the `.gitkeep` file) won't be. Use a `.gitkeep` file, plus a `!` rule in the main `.gitignore`.

### What _selectively_ means

What I want:

1. The developer runs the `get-hf` package script with the `ls` command.
2. The script prints a list of models with metadata.
3. Having reviewed the list, the developer manually edits the config file `server/scripts/get-hf/config.json` to specify which Hugging Face STT models he wants to make available for the end user (of the desktop app) to download and use.
4. The developer runs the `get-hf` package script with the `dl` command.
5. The script reads the config file and places the necessary assets and data into the `get-hf/data` dir.
6. The developer runs the server (`server/main.ts`), which reads `get-hf/data` and serves the assets and data therein in the way (format, paths, etc.) that the desktop app expects. **It mostly adheres to whatever Hugging Face API the desktop app uses. The idea is to conform the server to the desktop app's expectations, rather than the other way around.** In a sense, the server acts as a proxy for Hugging Face. However, **it does not make calls to Hugging Face**; it only reads the assets and data saved to `get-hf/data`.
7. The desktop app (modified to point at the aforementioned server, instead of at Hugging Face), in the situations in which it would have reached out to Hugging Face, will reach out to the server, and get the information it needs.
8. Thus, the end user will be able to see available local STT models, and download them.

## "Post Process" feature

Handy has a "Post Process" feature. In the version of Handy I have installed on my personal laptop (not this VM), the feature, and its tab in the sidebar, is hidden by default, and only shown if "Experimental Features" is toggled on (on the "Advanced" tab). 

- Hard-code it so that the "Post Process" feature is enabled and the "Experimental Features" toggle is removed.
- On the "Post Process" tab, remove the config options section titled "API (OPENAI COMPATIBLE)".
- The server, the same one that proxies Hugging Face, shall also proxy OpenRouter under the base path `/dictum/api/post-process/`. It shall be an OpenAI-compatible API, and it shall use OpenRouter's OpenAI-compatible APIs. The desktop app shall be hard-coded to use this custom endpoint. Handy's API config UI (that's being removed) already has a "Custom" option for "Provider"; just use the existing piping, and specify the "Base URL", "API Key", and "Model".
    - I want this feature to be implemented in a minimal and straightforward fashion. Think MVP. It might be as simple as removing some UI elements and writing a config file. I don't know; I don't know how Handy stores this config info. I don't want you to remove all the code for the other API options; just make them not appear in the UI. Approach this with the spirit of "minimum viable changes".
    - The model shall be hard-coded to `openai/gpt-5.6-luna`. This applies to both the desktop app and the server. The server, however, will disregard whatever model the desktop app client asks for in its "Post Process" requests, and it will use `openai/gpt-5.6-luna`.
    - **The desktop-app-to-server API key shall NOT be hard-coded in the desktop app**; it shall be input by the user as a non-skippable part of the "onboarding flow" (not sure what to call it)---the same through which the user picks a local model.
    - **The desktop-app-to-server API key SHALL be hard-coded in the server**, right in a TS file. Make its value `SAFE_FOR_TESTING`. (The idea is that this repo shall not be production-ready. It's more of a starter kit. It's up to the adopter to adapt the auth system to their needs.)
    - The **server-to-OpenRouter-API** API key shall live in `server/.env` and be called `OPENROUTER_API_KEY`. I have placed it there for you.
